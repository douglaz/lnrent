# Fable review — question 2 (is an attempt one concept?)

Reviewer: Claude Fable 5.1 subagent, read-only, 2026-09-14. Brief: `attempt-seam-review-brief.md`.

**Verdict:** Half right — the attempt *lifecycle + fence* is one concept (the seam that was missed twelve times), but the attempt's *money state* is not: a refund's is a per-Receipt fact with three amount bases and a backend-probed "started" state; a sweep's is per-row with one cap. Make the seam state-only; leave amounts and aggregation with each reader.

**Findings**

- [P1] `daemon/src/sweep.rs:103` (receipt gross), `daemon/src/ledger.rs:157` (row cap `amount_sat`), `daemon/src/store.rs:1285` (net `received_msat/1000`) — the *same refund row* commits three different amounts to three readers, while a sweep commits `max_outlay_msat` everywhere (`sweep.rs:170`, `ledger.rs:203`). "Committed" is three predicates over three bases, not one reader parameterised by kind. The question skips this prior one.
- [P1] `daemon/src/capture.rs:322-326` vs `daemon/src/sweep.rs:874-887` — a refund row is born PENDING at capture with no pay started; a sweep's PENDING row commits the backend PREPARED witness in the same txn. So "not started" is a real refund state and impossible for a post-#91 sweep, which is why `ledger.rs:69-80` needs a gen-keyed probe for refunds and `ledger.rs:202-206` needs none. This is a kind **parameter** only if "started" is defined as "pay-map row exists under `attempt.key()`" (`legacy_import.rs:793` vs `:823` is exactly that key function).
- [P2] `daemon/src/supervisor.rs:1808-1815` + `daemon/src/store.rs:1284-1297` — the readiness scan never reads the fence: a fenced PENDING refund whose backend answers "not started" (the fence's own premise) is priced into `required_msat` (`supervisor.rs:1864-1871`) *and* subtracted from `expected_msat` (`ledger.rs:69`) — double-counted, false `InsufficientBalance` (`supervisor.rs:1842`). Not in the brief's list.
- [P2] `daemon/src/supervisor.rs:1808` (parked = FAILED) vs `daemon/src/ipc.rs:1152-1166` (parked = fenced ∨ FAILED) — two definitions of "Parked" already in the tree; the glossary entry must pick one or split it (FAILED-parked is `refund-retry`-able, fence-parked is `clear-fence`-able).
- [P2] `daemon/src/refund.rs:135-137`, `daemon/src/sweep.rs:1072`, `daemon/src/ipc.rs:1264-1266` — a fenced FAILED row raises no RefundStuck/SweepStuck in either driver; the fence-as-flag decision is already made at `docs/adr/0022-backend-state-lives-in-the-books.md:430-434` (column, not status), so that "prior question" is settled, not skipped — cite it.
- [P3] `docs/specs/gate1-operator-sweep.md:167-168` — "Do NOT reuse the refund_attempt table — sweeps must never enter refund liability/readiness math". A one-concept answer that merges tables or readers contradicts the spec; a state-only seam does not.
- [P3] Readers the brief misses: `store.rs:1097-1105`, `:1209-1211` (GC keeps invoice/sub behind `status <> 'SENT'`); `legacy_import.rs:843-852`, `:1095-1108`, `:1114-1142`; `backup.rs:180-181` (same "correlation-bearing" predicate duplicated at `legacy_import.rs:1129-1130`); `supervisor.rs:1246` (`check_holdings_floor` consumes `expected_msat`). QUESTION: whether the backend-side `[8A]` `pay_other_key_for_hash` (ADR-0022:359, excludes FAILED rows) must also learn the fence — not read.

**Invariants the seam must answer (state-only):** re-attemptable (`PENDING ∧ ¬fenced`, `refund.rs:898-900`, `sweep.rs:766-767`); committed-to-wallet (`SENT ∨ fenced ∨ started(key)`); still-owed-to-buyer (refund `≠ SENT`; sweep never); needs-a-human (`FAILED ∨ fenced`); holds-the-slot (sweep `PENDING`, fenced or not, `sweep.rs:858-865`); keeps-receipt-alive (refund `≠ SENT`); correlation-bearing (`SENT ∨ backend_payment_id`).

**Reasoning**

Every fence miss in #91 was a reader re-deriving *state* (`status`, `migration_unverified_at`, started-evidence) — that is genuinely one concept, identical in both drivers (fence-first, CAS on `PENDING ∧ unfenced`, same alert gap). Put that in one `AttemptState` read, keyed by a kind-supplied `key()`.

What is not shared is *money*: `read_surplus` aggregates refunds per `external_id` and de-dups them against at-risk subscriptions (`sweep.rs:136,159`) — a refund's commitment is a facet of its Receipt (CONTEXT.md "at risk"), not of the row. Sweeps have no receipt, no generations, no INV-3 provenance guard, and one number. An `Attempt::committed_msat()` would have to take the *reader* as an argument for refunds and ignore it for sweeps: that is a different concept wearing a parameter. The upcoming writers (uxbd/gjwy adopt a wallet record onto a fenced row) mutate state only — `backend_payment_id`, status, fence — so a state-only seam is exactly what they need. The readiness double-count is a live example: it is a state omission (fence unread), not an amount problem.
