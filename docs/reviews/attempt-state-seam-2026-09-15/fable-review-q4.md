# Fable review — question 4 (who may read started evidence, through what?)

Reviewer: Claude Fable 5.1 subagent, read-only, 2026-09-15. Brief: `started-evidence-review-brief.md`.

**Verdict:** Direction right (surplus never reads it; by-ref probe stays outside), but Question 4 is moot as posed — post-ADR-0022 there is no "started evidence" distinct from `payment_status_by_key`, so the seam to build is one status read + one pure predicate + one snapshot per report, not a composed started-evidence reader.

**Findings**

- [P2] `daemon/src/phoenixd_backend.rs:2218-2232`, `daemon/src/lnv2_backend.rs:1408-1422` — `payment_started_by_key` is literally `pay_status_by_key(..).is_some()` and `payment_status_by_key` is `map_pay_status(pay_status_by_key(..))` with `None => Unknown` (`lnv2_backend.rs:480-487`, `phoenixd_backend.rs:996-1003`; every written status — PREPARED/PENDING/SUCCEEDED/FAILED — is mapped). So `Unknown ∧ started` is unreachable on both shipped backends and on `MockPayment` (default `false`, `backends.rs:276`). The branches at `ledger.rs:79`, `supervisor.rs:1868,1881`, `sweep.rs:537`, `refund.rs:541-548` are dead; the ledger/refund/sweep test doubles (`ledger.rs:239-253`, `refund.rs:1443`, `sweep.rs:1421`) pin an unreachable state. Committed = SENT ∨ fenced ∨ status ∈ {Succeeded, Pending}.
- [P2] Brief's caller census is wrong: `order_intake.rs:1653+`, `ipc.rs:1891+`, `reconcile.rs:2255` are all inside `#[cfg(test)] mod tests` (starts at 1440 / 1713 / 1628). Production callers are exactly four modules: `ledger.rs:76-79`, `supervisor.rs:1866-1882`, `refund.rs:531,544,622,920,928`, `sweep.rs:537,953,965`. There is no "non-money caller that must keep calling the backend directly"; item 2's last bullet has an empty answer.
- [P2] `supervisor.rs:1760-1761` then `1866`/`1879` — two observations per report: `expected_msat` probes every `refund_attempt` row, then readiness re-probes each PENDING one. A PREPARED write (`refund.rs:900-907`) or an lnv2 `mark FAILED` (`lnv2_backend.rs:857`) between them double-counts the row on both sides of `expected < required` (`supervisor.rs:1842`) — a one-tick false Insufficient/READY in `lnrent money`/the log. "One reader" does not fix this; one snapshot does. Log-only today (`supervisor.rs:1583` — readiness never dispatches), so P2 not P1.
- [P3] TOCTOU: none introduced. The only intent-writing gate reads the sync surplus in-txn (`sweep.rs:868`) and commits the PREPARED witness in the same txn (`sweep.rs:874-887`); the refund authorising txn CASes `status='PENDING' AND migration_unverified_at IS NULL` (`refund.rs:899-906`). No intent write consumes `expected_msat` or the readiness verdict (callers: `supervisor.rs:1256`, `ipc.rs:808,851` only).
- [P3] `CONTEXT.md:187-191,213-217` "provably started paying" overstates PREPARED: on lnv2 the op may not exist yet (`lnv2_backend.rs:802-817` re-runs the cap when Missing); phoenixd has no PENDING at all. Direction is conservative and self-heals next drive (`phoenixd_backend.rs:1528-1531`), so wording only: "the daemon has committed a pay witness for it".
- [P3] Brief's rejection rationale for the SQL-join alternative ("key derivation belongs to each backend") is false for refunds: `ledger.rs:75` and `supervisor.rs:1865,1878` already call `refund::gen_key`. The real reasons are per-backend table ownership and the mock having no table. Rejection still stands; fix the reason.
- [P3] Drivers' reads (`already_paid`, `plan_payment`'s status-first, `status_by_key_after_error`, `recovery_status`) are lifecycle decisions needing the 4-way `PayStatus`, not a money bool. A seam that returns raw evidence serves them; one that returns `committed` must not.
- QUESTION: whether uxbd/gjwy audit adoption goes through the existing `commit_sent` CAS (`sweep.rs:977-989`, `refund.rs:945`) — the bead text was not read here; the seam should stay read-only either way.

**Suggestions (smallest shape)**

1. Delete `payment_started_by_key` (trait default, 2 impls, 4 call sites, 5 test doubles). `Unknown` now means "no witness row".
2. One pure fn, e.g. `ledger::committed(lifecycle: &str, fenced: bool, pay: PayStatus) -> bool`, used at `ledger.rs:69-80` and `supervisor.rs:1866-1869,1879-1882` (readiness must then load `migration_unverified_at` in `store.rs:1284-1287` — closes lnrent-4br3 in passing).
3. One snapshot: `ledger::refund_commitments(store, payment) -> Vec<RefundCommitment{.., pay: PayStatus}>` probed once; `expected_msat_from(&reads)` becomes pure; `refund_readiness_report_with_probe` builds the vec once and looks up its liabilities by `external_id` instead of re-probing.
4. Drivers call a thin `attempt_pay_status(payment, key)` wrapper (same module as 2) — no row re-read, no fence re-read; they already hold the row.
5. The runnable check: add `lnrentd::backends::PaymentBackend::payment_status_by_key` to `clippy.toml`'s `disallowed-methods` with `#[allow]` only on the wrapper (pattern: `backends.rs:57`, `lnv2_backend.rs:1208`). CI already runs `cargo clippy --workspace --all-targets -- -D warnings` (`.github/workflows/ci.yml:53,131`), so add `#![allow(clippy::disallowed_methods)]` to the test modules in `sweep.rs`, `refund.rs`, `ledger.rs`, `ipc.rs` (as `order_intake.rs:1443` does). Break-test: put one direct call back in `supervisor.rs` and confirm clippy fails.

**Reasoning**

The design under review assumes three inputs (lifecycle, fence, started). Reading the two backend impls shows started and status are one SQLite row read; the distinction existed when lnv2's started signal came from the fedimint oplog (kum) and the index was a side file. ADR-0022 moved the PREPARED witness into the authorising transaction, so "row exists" is now the whole started story, and the wallet's own history has its own seam (`outbound_status_by_ref`). Once that collapses, the remaining real defect is not "who reads" but "how many times per report": readiness and the ledger observe a reversible predicate twice and compare across the flip. A per-report snapshot is the fix; a composed reader alone changes nothing. The sweep gate needs none of this — its PENDING row and witness commit together, and `read_surplus` counts by status. The clippy deny is the right check because CI runs clippy over all targets with `-D warnings`; it fails on a bypass rather than merely counting call sites.
